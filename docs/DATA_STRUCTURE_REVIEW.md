# Kome Data-Structure Review

## 1. Executive summary

**Yes — the current design is efficient for the stated workload, and no structural data-structure swap is justified by the evidence.** Every mutating operation in Kome is dominated by Ed25519 sign/verify (44–130 µs) or by fsync latency, three orders of magnitude above anything a different container could save (`std::map` point operations run in tens of nanoseconds). The nested `std::map<string, std::map<string, Entity>>` index, the Bitcask-style append-only log, and the flat sorted-vector-plus-prefix-sum RBSR snapshot are each the structure the field independently converges on for this exact shape of workload (full state in RAM, personal scale, no beyond-RAM reads, authenticity from per-record signatures rather than a Merkle history). `DECISIONS.md`'s existing rejection of Prolly/Merkle-Search-Trees is correct, and this review's independent literature pass and adversarial re-verification of five analysts' proposals reached the same conclusion by a different route.

That said, five implementation-level changes are worth making — none of them touch the container types, all of them close real, *measured* gaps in how those containers are used:

1. **Stream compaction instead of building the full log image in RAM** (storage.cpp) — removes a measured ~29 MB transient RSS spike at 50k entities, growing to 100–300 MB at the top of the stated scale, which is exactly the Android low-memory-kill window.
2. **Batch the blob-chunk write path through the storage layer's existing transaction batching** — cuts fsyncs by ~55× for a multi-MB blob (measured), but *must* ship with sub-frame flushing, because naive batching was measured to make peak memory 2.3× *worse*, not better.
3. **Cache each cell's reconciliation-element hash at mutation time** — cuts the cold RBSR snapshot rebuild's crypto cost by ~2.7×, wire-compatible, no version gate, ~32 B/cell.
4. **Serve read-scoped RBSR snapshots as range views over the cached full snapshot**, applied first to time-bound-capability peers (an unambiguous win) — removes a full O(N) re-encode+re-hash that a capability-restricted or expiring-capability peer currently pays every gossip cycle, including when idle.
5. **Split `state_gen` into a content generation and a scope generation** — a capability grant/revoke currently invalidates and fully rebuilds the unscoped RBSR snapshot even though no data changed; this is a few lines and composes with #4.

Four further proposals (author-pubkey interning, a flat-map for `Entity::fields`, skipping signature re-verification on load for encrypted logs, and an autocompaction policy knob) are directionally reasonable but rest on cost/benefit numbers that turned out to be off by a meaningful factor once measured — they belong on a benchmark backlog, not in the codebase, until someone runs the number that would actually decide them. A longer list of structural alternatives (hand-rolled B-tree/ART index, hash+sorted-index hybrid, flat composite-key map, LSM storage engine, LMDB-style B-tree pager, Prolly/MST, mutable in-place RBSR tree, MAC'd load checkpoints) was seriously evaluated across the five reader/analyst passes and is recorded below as rejected, with the specific reason each one fails — precisely so it does not get re-proposed without first reading this document.

## 2. What Kome uses today

| Subsystem | Structure | Location | Per-unit cost | Dominant cost driver |
|---|---|---|---|---|
| In-memory index | `std::map<string, std::map<string, Entity>>`; `Entity` = LWW presence (`bool`+`Hlc`+`PubKey`+`Sig`) + `std::map<string, Register>` fields | `engine.hpp:72-73`, `:57-70`, `:42-47` | ~109 B/entity presence + ~48 B empty field-map + ~108 B fixed (12 B HLC + 32 B author + 64 B sig) + value per field register | Ed25519 sign (42–130 µs) / verify (~130 µs) on every mutation and applied record — container ops are 3 orders of magnitude cheaper |
| Storage log | Bitcask-style append-only file; write-through per-mutation fsync; compaction rewrites one frame/entity from RAM; 30-day tombstone GC | `storage.h:39-134`, `storage.cpp` | ~114 B + key/value per on-disk ENTITY/FIELD frame (`storage.cpp:142-169`) | Reopen is signature-reverification-bound: ~130 µs/record → ~3.5 s at 100k records (measured, 4 cores); per-mutation fsync bounds write latency |
| Sync snapshot & digest | `ReconSnapshot`: sorted `vector<Element>` (`SortKey`+canonical bytes+SHA-256) + prefix-sum `Hash256` array; `shared_ptr` cached per `state_gen`; per-peer `scoped_cache` (up to `kMaxScopedCache`=256 entries) | `reconcile.cpp:70-74, 61-65, 54-57`; `engine.hpp:107-120` | ~330–350 B/element (SortKey ~120 B + bytes + 32 B hash); a full duplicate copy of every peer's visible state while cached | Cold rebuild is ~63% per-element SHA-256, O(N) (`PERF.md`); steady state is O(1) via generation-cache (~15 ns, `PERF.md:104`) |
| Blob layer | Pure wrapper over `sync_engine_set/get/delete`; 32 KiB chunks keyed `'c\0'+hash`; manifest `'b\0'+id` | `blob.cpp:37-58, 143-199` | 34 B stack key; manifest ~20 B + 32 B/chunk hash | One fsync'd transaction per 32 KiB chunk, unbatched — measured ~1000 fsyncs for a 31 MiB blob |
| Capability store | Two flat `std::vector<Capability>`/`<Revocation>`, linear dedup scan on insert, `by_issuer` index rebuilt fresh on every authorization call | `capability.h:73-123`, `capability.cpp` | ~150 B/capability or revocation, capped at 4096 ingested | O(N) per write-authorization check; not cached across calls |

**In-memory index.** Full state lives in two levels of `std::map` so that byte-lexicographic order — which RBSR, `sync_engine_scan`'s exclusive `upper_bound` cursor (`sync_engine.cpp:505`), and `sync_engine_digest`'s determinism all depend on — comes for free from the container rather than from an explicit sort. Every `Register` (a field value) carries its own 12 B HLC, 32 B author pubkey, and 64 B EdDSA signature; every `Entity` carries the same trio for its presence assertion. That is 108–172 B of fixed cryptographic overhead per cell before the value or field-name bytes are counted, and it is intentional: it is what makes every cell independently authenticatable off the wire or off disk.

**Storage log.** The log is Bitcask-shaped by design: because full state lives in RAM, the file's only jobs are durability, crash atomicity, and a bounded size — not query serving. Frames are length-prefixed and checksummed (or AEAD-sealed if encrypted); a torn tail is truncated on the *next* write, never destructively at open (`storage.cpp:661-717`), a subtlety added after a real nightly-test flake (`DECISIONS.md`). Compaction rewrites the log as one frame per live entity and drops tombstones older than 30 days in place over the engine's own maps (`storage.cpp:826-843`). Every mutation is its own fsync'd frame today — batching exists (`Storage::batch_begin/batch_commit`, used internally by `reconcile.cpp:415-455`) but is not exposed for local bulk writes.

**Sync snapshot & digest.** RBSR needs combinable range fingerprints over an ordered set; Kome gets O(1) fingerprints for any range via a prefix-sum array of 256-bit hashes (`add256`/`sub256`, `reconcile.cpp:116-139`) over a flat, immutable, `shared_ptr`-shared snapshot, rebuilt lazily when `state_gen` advances (`engine.hpp:107-108`) and cached per read-scoped peer in `scoped_cache` (`engine.hpp:119-120`). `sync_engine_digest` is a separate O(N) SHA-256 walk over the sorted maps (`sync_engine.cpp:762-800`) with zero internal callers — it exists purely as a convergence oracle for tests and examples.

**Blob layer.** Blobs are not a separate storage mechanism; `sync_blob_put`/`get`/`delete` decompose a payload into 32 KiB chunks, hash each with BLAKE2b, and write each chunk plus a manifest through the ordinary `sync_engine_set` path (`blob.cpp:143-199`) — so chunks inherit LWW semantics, replication, and per-record signing for free, at the cost of one signed, fsync'd transaction per chunk.

**Capability store.** `CapStore` holds two unbounded-but-capped (`kMaxIngestedCaps`/`kMaxIngestedRevs` = 4096) flat vectors, searched linearly for dedup on insert and walked via a temporary `by_issuer` index built fresh on every `authorized()` call (`capability.cpp:212-248`) — this sits on the write-authorization hot path and was cataloged but not put through a verdict-checked recommendation in this research pass; it is flagged here as an open area for a follow-up review rather than assessed.

## 3. Recommendations

### 3.1 Endorsed — ranked by value

**1. Stream compaction to the temp file instead of building the full log image in RAM.**
Change: rework `Storage::compact`/`serialize_state` (`storage.cpp:724-784, 845-854`) to write each sealed frame incrementally to `<path>.tmp`, then fsync + rename as today, instead of accumulating one `std::string` holding the entire new log.
Verified cost: compacting 50k entities (17 MB log, ~30 MB live RSS) measured a +29.1 MB VmHWM transient (48.5→77.6 MB) — ~1.7× process memory, growing to an estimated 100–300 MB at 200–500k records. That is exactly the Android low-memory-kill window.
Corrections found during verification: the encrypted path adds one entity's ciphertext buffer per frame, not a second full image as originally claimed; the WASM benefit is smaller than stated, since Emscripten's MEMFS already holds a second copy of the file bytes in the JS heap — streaming roughly halves the transient there, it does not bound it to one frame. The deferred open-time compaction heuristic (`fresh.size()*2 < file_size_`, `storage.cpp:864`) currently needs the final image size *before* writing it; streaming needs either a cheap size-only dry pass or accepting a discard-and-unlink after the fact. Crash safety, the digest-unchanged-across-compaction property, and the erase→tombstone→compact physical-erasure guarantee are all unaffected (frame bytes stay byte-identical; rename stays the commit point). Confidence: high.

**2. Batch the blob-chunk write path through the existing `Storage::batch_begin/batch_commit`.**
Change: expose thin ABI wrappers over the already-used batching machinery (`storage.cpp:362-380`) and wrap `sync_blob_put`'s chunk loop (`blob.cpp:150-171`) in a batch, flushing sub-frames every ~1–4 MiB.
Verified benefit: a prototype measured a 55× fsync reduction for an 8 MiB blob (273→5 fsyncs, 7→1 rename).
Correction that changes the shape of the fix: the originally claimed "~2× less write I/O" did not hold (measured 18.10 MiB vs 16.17 MiB written — a 10% saving, from the byte count, not the fsync count) and, more importantly, naive batching was measured to make **peak memory 2.3× worse** (+17.9 MB → +41.7 MB for an 8 MiB blob), because `staging_` holds the whole blob and is then copied again in `seal_frame` and again in `make_frame_full` (plus a third ciphertext copy if encrypted). The sub-frame flush is therefore **mandatory, not optional**, and should ship together with recommendation 3.1 rather than as a standalone change. Two implementation hazards to close before shipping: `batch_begin`/`batch_commit` have no nesting guard (an embedder batch around an internal reconcile-apply batch would silently close the outer one) and no rollback on a mid-batch failure. `sync_blob_erase`/`sync_blob_delete` (N+1 and 2N+1 fsync'd mutations respectively) deserve the same treatment and were not covered by the original proposal. Confidence: high.

**3. Cache each cell's 32-byte reconciliation-element hash at mutation time.**
Change: add a `Hash256` to `Register` and to `Entity`'s presence assertion, computed at the same points that already bump `state_gen` (`sync_engine_set`, `sync_engine_delete`, both branches of `apply_change`), so `build_snapshot` copies a stored hash instead of recomputing SHA-256 for unchanged cells.
Verified benefit: `PERF.md` attributes ~63% of the post-cleanup cold rebuild to per-element SHA-256; the measured/derived numbers (~1 µs/element at N=4096 against a 0.8 µs SHA-256(64 B) baseline) support a ~2.7× cut (8.2 ms → ~3 ms at N=4096, extrapolating to roughly 50 ms → 18 ms at 100k cells). Wire-compatible — the fingerprint values are byte-identical, so unlike the BLAKE2b element-hash idea already on `PERF.md`'s backlog, this needs no protocol version gate. Cost: ~32 B/cell (~3.2 MB at 100k cells).
Three implementation hazards surfaced during verification and must be handled, not just "watched for staleness": (a) `storage.cpp:445-446`'s dominance check can default-insert a `Register` that ties the comparison and is left unassigned — its cached hash must be set on *insertion*, not only on a winning assignment, or the cell's fingerprint silently and permanently diverges; (b) `sync_engine_erase_field` is not a separate mutation point (it delegates to `sync_engine_set`), and `sync_engine_set` can touch *two* cells (presence + register) in one call, so both need hash updates; (c) the hash cannot be computed inside the existing parallel load-verification pass as originally proposed — that pass materializes only the pre-signature signing bytes, while the element hash must also cover the trailing 64 B signature, so it needs its own pass. Confidence: high.

**4. Derive read-scoped RBSR snapshots as range views over the cached full snapshot — apply first to time-bound-capability peers.**
Change: because RBSR elements sort ns-major (`reconcile.cpp:80-86`) and read scoping is applied once per namespace (`reconcile.cpp:588`), a peer's visible set is a union of contiguous ranges of the full snapshot. Replace `build_filtered`'s full re-encode+re-hash (`reconcile.cpp:648-654`) with a view: the shared full snapshot plus a small per-namespace range/cumulative-fingerprint table, indexed through `sync_session`'s existing `snap()`/`prefix()`/`lower_index()` accessors.
Verified cost this removes: `reconcile.cpp:716` never caches the filtered snapshot for a time-bound-capability peer, so it pays a full O(N_visible) encode+SHA rebuild *every gossip cycle*, confirmed to include idle, converged links (`SecurePeerSession::poll → kick_ → begin_cycle_`, `connection.cpp:82,90,167`) — a sustained, avoidable battery cost on a phone.
Correction that changes where to apply this first: the claim that this is "the normal configuration" is false — `ensure_scoped_cache` already fast-paths fully-open peers onto the shared unscoped snapshot (`reconcile.cpp:684, 718-719`); the expensive path requires capabilities engaged *and* at least one denied namespace. For a single restricted peer seeing a small fraction of state, forcing a full base-snapshot build can make CPU and memory *worse* than today's smaller targeted rebuild — the win requires either several restricted peers whose visible fractions sum past 1, or (unambiguously, regardless of fraction) a time-bound peer, where the base becomes cacheable across cycles precisely because it no longer depends on scope. Implementation touches roughly eight call sites that currently index the raw vector directly (including a DoS-bound size computation at `reconcile.cpp:813` that must use the visible count, not the base count), and the deadline-cached variant needs `CapStore::authorized()` extended to return an earliest-expiry timestamp, not just a bool (`capability.h:108-111`). Correctly flagged residual risk: after this change a scoped session object can physically hold out-of-scope bytes; correctness depends on index arithmetic rather than physical absence, so it needs a debug assert comparing against a from-scratch build. Confidence: high on the mechanism; scope the rollout to time-bound peers first, then measure real peer/namespace-fraction distributions before extending it to all restricted peers.

**5. Split `state_gen` into a content generation and a scope generation.**
Change: `state_gen` today is bumped both by content mutation and by pure capability changes (`capability.cpp:282, 309, 442, 474`), and `ensure_cache` keys the content snapshot on it (`reconcile.cpp:659`) — so every capability grant, wire-ingested delegation, or revocation throws away and fully re-encodes and re-SHA-256s the unscoped snapshot with zero cells changed. Separate a `content_gen` (bumped only by set/delete/apply/gc_tombstones) from a `scope_gen` (bumped only by capability changes), and key the base snapshot cache on `content_gen` alone.
Benefit: no new data structure, a few lines, strictly cheaper than recommendation 4 by itself, and composes with it — the same cache invalidation boundary is what recommendation 4's view layer sits on top of. Confidence: high (this was surfaced and validated during verification of the "keep the RBSR architecture as-is" assessment, not in the original recommendation list).

**6. Keep the remaining architecture as-is, with two corrected justifications.**
No code change for the nested `std::map` index, the Bitcask log design, or the flat sorted-vector-plus-prefix-sum RBSR snapshot; defer the incremental-digest backlog item. Two things worth recording precisely, since they change *why* this holds rather than *whether* it holds:
- The originally-cited justification that alternatives to `std::map` would break "reference stability" (a live pointer/reference held across a mutating insert) does not hold — an exhaustive grep of every `Entity`/`Register` reference site found none held across a mutation. The container choice is still correct, but for the surviving reasons: free byte-lex ordered iteration and `upper_bound` cursors that RBSR/scan/digest rely on, and a crypto-bound cost floor on every *mutating* op. Note this floor does not cover `get`/`scan`/`exists`, which carry zero crypto, so container cost is 100% of the read-path cost there — and the 48 ns `get` benchmark was run on a one-entity engine, so it establishes nothing about lookup cost at 10⁵ keys. The read path is genuinely unmeasured at scale, not proven fast.
- `sync_engine_digest` should stay O(N) and deferred: it has zero internal callers (confirmed by grep — only tests, examples, and bindings call it), and cheaper substitutes for its two real uses already exist (`state_gen`/`content_gen` for local-change detection; the already-O(1), 37-byte no-op RBSR sync for cross-replica equality). If it is ever made incremental, the update surface is wider than "the mutation points plus tombstone GC" — it must also cover implicit entity creation in the REGISTER branch of `apply_change` and in `merge_decoded`, either of which silently and permanently corrupts the digest if missed. (This list originally named a third site, the unasserted-shell path of `apply_entry`. Both halves of that are now obsolete: the digest no longer hashes a presence block for an unasserted entity at all, and `apply_entry`'s shell-materialising `(void)e->ns[ns][ent]` is gone — see DECISIONS.md, "Zero-HLC existence records". The hazard this paragraph anticipated for a *hypothetical* incremental digest turned out to be live in the O(N) one, which is what forced that fix.) That risk, not the O(N) cost itself (corrected from the original ~80 ms estimate to ~39 ms at 100k cells), is the strongest reason to leave this deferred until an application demonstrates hot digest polling.

### 3.2 Worth benchmarking (uncertain — gate on a measurement, not on this review)

**Intern author `PubKey`s into a per-engine pool.** Real saving, but smaller than claimed once measured layouts are used: ~56 B/cell (not 28 B), ~5.6 MB at 100k cells, ~12% of index RAM — real, but the ReconSnapshot duplicate (~330–350 B/element, up to 256 cached scoped copies) is a larger memory item sitting right next to it. The hazard surface is worse than originally flagged: the author bytes participate directly in the LWW tie-break comparison (`register_cmp`, `existence_cmp`, `apply_change`'s dominance memcmp), so comparing pool indices instead of raw key bytes risks peers resolving ties differently — permanent silent divergence detectable only via the digest oracle; `Storage::load` drops records that fail signature re-verification on reopen, so a pool mis-mapping would manifest as silent data loss, not a crash; and `apply_change` holds a raw pointer into the author array, so the pool needs a stable-address container (deque/chunked), not a `vector`. Gate on an actual RSS measurement — and expect the snapshot layer, not this, to be the bigger finding if that measurement is taken.

**Flat sorted small-vector for `Entity::fields`.** The measured per-entity saving is 24 B (not 48–64 B as claimed: `sizeof(std::map)`=48, `sizeof(std::vector)`=24), and the argument is made from 64-bit `libstdc++` numbers while the actual constrained target — Emscripten/`libc++` on wasm32 — has roughly half the per-node overhead, so the win on the platform that motivates it is about 2× smaller than argued. No ordering or reference-stability invariant breaks (verified by grep and by the fact that `std::string`'s unsigned byte-lex comparison matches `std::map`'s default order exactly). The performance half of the benefit is a small slice of an already-small remainder (the cold rebuild is ~63% SHA-256; this touches only the non-hash ~37%). Real but modest (~5.6 MB at 100k cells, ~28 MB at 500k); bundle only with a broader, measured memory effort, not on its own.

**Skip per-record Ed25519 re-verification on load for encrypted (AEAD-authenticated) logs.** The reopen cost is real and measured (3.52 s at 50k entities / 100k records, 4 cores; WASM has no parallelism, so the browser worst case is the full serial figure). But the claimed speedup does not hold: stubbing verification measured 0.35 s, i.e. a 10× (parallel) to ~37× (extrapolated serial) win — not the claimed 100–1000×, which mistook a 34 ns/record codec microbenchmark for the whole non-crypto load cost (the real figure is ~3.5 µs/record). The security argument for skipping it is actually *stronger* than originally stated — the identity seed lives inside a sealed frame in the same file, so anyone who can produce an AEAD-valid frame already holds the key needed to mint arbitrarily many correctly-signed owner records, meaning Ed25519 re-verification protects against nothing from that adversary — but the residual protection it does still provide was mis-scoped: it is what stops a key-holder from forging a record falsely *attributed to a different peer's pubkey* (a narrow but real "Bob said X" spoof on Alice's own device). This edits a headline guarantee in `SECURITY.md` and the documented S2 decision, and only helps encrypted logs — not the plaintext default that `komed` and the test suite use. Take it to the maintainer as a deliberate posture decision, with the corrected 10–37× number, not as a drop-in optimization.

**Autocompaction policy knob (let embedders defer compaction to idle/charging time).** The write-path spike is real and larger than assumed: 60,000 sequential local writes measured a worst-case 182.8 ms and second-worst 104.3 ms single `set()` call, on warm cache / near-free fsync hardware — Android flash will be worse. No invariant breaks (compaction is already a public, explicitly-invoked operation). But this is a permanent new ABI surface for a cost that is bounded and amortized, proposed with no embedder report yet, and a cheaper non-ABI fix is already parked in `docs/DATA_TODO.md`: a dead-fraction compaction trigger instead of the current pure size-doubling rule, which would reduce the *number* of rewrites for an all-live, steadily growing dataset — exactly the shape the 60k-write benchmark exercised (7+ full rewrites, nothing dead). Evaluate that first; add the knob only if a real embedder reports the spike.

### 3.3 Considered and rejected

These structural alternatives were evaluated in this research pass (readers and analysts) and refuted with specific evidence. Recorded here so they don't get re-proposed without this context.

- **Hand-rolled B-tree or adaptive radix tree (ART) replacing the `std::map` index.** Rejected on the crypto-bound cost floor for every mutating path (sign 42–130 µs vs. container ops in nanoseconds) and on trusted-code-base size (1–2k LOC of node-management complexity in the signed-record path, or a vendored dependency, against a project that dropped SQLite specifically to stay small and dependency-free). Not rejected on "reference stability," as one analysis originally argued — that claim was checked and found false (no code holds a node reference across a mutating insert). The genuinely open question this leaves is the *read* path (`get`/`scan`/`exists`, zero crypto), which is unmeasured at 10⁵ keys, not proven fast by the existing 48 ns single-entity benchmark.
- **Hash map plus a separately maintained sorted index.** Rejected: doubles cache-invalidation complexity to speed up a 48 ns lookup that sits three to four orders of magnitude below every operation that touches signing, and forfeits the ordered iteration that RBSR, `scan`, and `digest` get for free from `std::map`.
- **Flat map on a single `(ns, entity, field)` composite key.** Rejected: entity/field bytes may contain any byte including NUL, so naive length-prefixing does not preserve byte-lexicographic order (it orders by length before content); an order-preserving encoding would be more complex than the two-level map it replaces, and the saving is only ~48 B per namespace — namespaces are few.
- **Sorted vector with batched rebuild for the index.** Rejected: per-insert `memmove` makes replay and bulk-apply O(N²), and invalidates every outstanding reference across a mutation.
- **LSM-tree storage engine.** Rejected: LSM solves beyond-RAM reads and sustained high-throughput write ingest, neither of which applies here (full state lives in RAM at personal scale) — it would add memtables, SSTables, levels, and compaction tuning for no measurable benefit, consistent with what comparable systems (Automerge-repo, Yjs providers) do at this scale: append-plus-size-triggered-merge, not LSM.
- **LMDB-style B-tree pager for storage.** Rejected: measured reopen cost is 3.52 s, of which ~3.17 s is Ed25519 verification; a pager's O(1) tree-reopen would save at most the remaining ~10% while adding an external dependency the project explicitly avoids, and does not touch the actual bottleneck.
- **Prolly tree / Merkle Search Tree**, for either storage layout or sync fingerprints. `DECISIONS.md`'s existing rationale holds — Kome keeps only current LWW state, not history to diff, and RBSR's stateless, DoS-resistant properties are worth more here than structural sharing — plus a storage-specific point confirmed in this pass: per-mutation fsync would become an O(log N) path-to-root rehash-and-rewrite instead of one appended frame. One originally-stated objection does not hold cleanly: "content-addressed sharing conflicts with the physical-erasure guarantee" is in tension with Kome's own blob layer, which is already content-addressed with no chunk refcounting and documents the identical shared-chunk erasure caveat — so that specific point is a cost Kome has already accepted once elsewhere, not a clean disqualifier for Prolly/MST. The O(log N)-per-write argument is the one that actually carries the rejection.
- **Mutable, in-place-edited RBSR snapshot** (a tree updated incrementally instead of rebuilt and swapped). Rejected: breaks the immutable, `shared_ptr`-shared-snapshot invariant that keeps in-flight reconciliation sessions safe against concurrent local applies; a persistent/copy-on-write monoid-annotated tree could match this in principle but is materially more complexity than current write rates justify. Recorded as the known upgrade path if write-rate × state-size × peer-count grows past what lazy rebuild-on-`session_begin` can amortize — not adopted now.
- **A MAC'd index checkpoint to speed up load**, for plaintext logs. Rejected as unsound: the identity seed used to key such a checkpoint lives as a plaintext META entry in the very same file, so a file-swap adversary who can already forge records could forge the checkpoint too. (The premise behind wanting this — that non-crypto load cost is negligible — was itself corrected upward, from an assumed 34 ns/record to a measured ~3.5 µs/record; the conclusion still holds because the crypto cost, ~130 µs/record, remains ~40× larger.)

## 4. What the field does

Grounding: `docs/STORAGE.md`, `docs/PERF.md`, `DECISIONS.md`, and the source files above, cross-checked against the following.

**In-memory index.** Main-memory databases move to cache-conscious ordered structures — adaptive radix trees ([Leis, Kemper & Neumann, ICDE 2013](https://dl.acm.org/doi/10.1109/ICDE.2013.6544812)) or B-tree maps ([Abseil B-tree design note](https://abseil.io/about/design/btree), ~40 B/value red-black overhead vs. ~4.3–5.1 B/value for `absl::btree_set`) — specifically when the index itself is the bottleneck. CRDT libraries proper use structures shaped for *sequence* CRDTs that don't transfer here: Yjs keeps doubly-linked-list items with cached search markers ([INTERNALS.md](https://github.com/yjs/yjs/blob/main/INTERNALS.md)); Automerge 3 moved to using its compressed columnar wire format as the runtime representation itself (700 MB → 1.3 MB on the "Moby Dick" benchmark, [Automerge 3.0](https://automerge.org/blog/automerge-3/)). The closest-shaped systems (Earthstar/Willow entry stores) sit on generic ordered key-value structures wrapped with fingerprint summaries — structurally the same layering Kome uses. Given Kome's measured 48 ns `get` sits under a 130 µs verify floor, this literature supports keep-as-is; it also supports the review's finding above that a vendored B-tree map (Abseil-style), not ART, would be the correct lever *if* RAM ever becomes the binding constraint, since it needs no new dependency to implement by hand.

**Storage.** The pattern matches field practice exactly. [Bitcask](https://riak.com/assets/bitcask-intro.pdf) is append-only files plus an in-RAM keydir, explicitly built on the assumption that keys fit in RAM — Kome's stated design point. Automerge-repo appends incremental change chunks and compacts into a snapshot "when incremental bytes exceed the compressed-document size" ([storage docs](https://automerge.org/docs/reference/under-the-hood/storage/)) — the same amortized-doubling trigger as Kome's. Yjs persistence providers do the same append-then-merge ([document updates](https://docs.yjs.dev/api/document-updates)). LSM trees are the field's answer to *write-heavy, larger-than-RAM* workloads ([Luo & Carey survey](https://arxiv.org/abs/1812.07527)), which is not this workload. Where the field diverges from Kome's current numbers: Bitcask trusts a CRC and neither Automerge nor Yjs re-verifies signatures on load, so Kome's re-verify-everything reopen cost (~3.5 s at 100k records, corrected above from an earlier, larger estimate) is a self-imposed and unusually strict threat model (protecting against a swapped/tampered file) — defensible, but the one place Kome pays a cost the field's comparable systems don't, which is why the parallel-verification fix (already in the codebase, just not exposed for encrypted logs, §3.2) and not a checkpoint format is the right lever.

**Sync protocol.** RBSR is the current consensus for this exact problem shape: [Meyer, "Range-Based Set Reconciliation," SRDS 2023](https://arxiv.org/abs/2212.13567); [negentropy](https://github.com/hoytech/negentropy) (used by nostr/strfry); [Willow's 3d-RBSR](https://willowprotocol.org/specs/rbsr/index.html); [Earthstar range-reconcile](https://github.com/earthstar-project/range-reconcile). Kome's fingerprint — SHA-256(count ‖ Σ SHA-256(record) mod 2²⁵⁶) — is structurally identical to negentropy's, and Kome's measured behavior (37-byte constant no-op poll, ~3 RTTs, bandwidth proportional to the actual diff) matches what the field reports for RBSR. Two field techniques are worth naming explicitly:
- **Incremental fingerprint maintenance.** Meyer §4 formalizes monoid-labeled search trees that cache each subtree's fingerprint and update it in O(log n) per mutation, extended to B-trees; negentropy's `BTreeLMDB` backend and willow-js's summarisable skiplists do this in practice (strfry reports 4–10× on anti-entropy). This is the field's documented answer to exactly the O(N) rebuild §3.1 recommendation 3 shrinks by a constant factor — it is the correct *next* step if write-rate × state-size × peer-count outgrows what lazy, gen-cached rebuild can amortize, and it is why the mutable-tree alternative in §3.3 is recorded as a future path rather than a rejection of the idea outright.
- **Fingerprint security.** The additive-hash family Kome uses (like negentropy's) reduces collision-finding to the k-sum problem, breakable subexponentially by [Wagner's generalized birthday attack](https://link.springer.com/chapter/10.1007/3-540-45708-9_19); Hoyte's practical analysis for negentropy found naive addition mod 2ⁿ collides in tens of hours of attacker compute. Kome is at 256 bits (negentropy ships 128-bit truncated), which is strictly stronger than the field's main deployment, and already includes the record count in the fingerprint as Meyer/Hoyte recommend as a partial mitigation. The one field-endorsed, cheap additional mitigation Kome does not yet take is randomizing split-bucket boundaries per session rather than using fixed equal-count buckets — worth a line in `SECURITY.md` documenting the accepted risk (a liveness/non-convergence attack by an *already-authorized* malicious peer, not a forgery), and worth the randomization as a follow-up.
- **A concrete, field-standard fix for a bug Kome already has on record.** Negentropy enforces a `frameSizeLimit` on every protocol message, trading round trips for a bounded frame size. `DECISIONS.md` records an open bug where unchunked HAVE/transfer messages exceed the relay's 64 KiB cap at roughly 90 changed records, silently breaking relay-routed sync. This is the single most actionable, field-grounded finding in the survey that this document has not yet run through adversarial verification — it should be the subject of a focused follow-up review before implementation, since it wasn't part of the verdict-checked recommendation set above.

**Digest.** Incremental/homomorphic multiset hashing is established practice for exactly this "cheap convergence check" role — [Clarke et al., ASIACRYPT 2003](https://link.springer.com/chapter/10.1007/978-3-540-40061-5_12); LtHash ([Lewi et al., eprint 2019/227](https://eprint.iacr.org/2019/227)) is deployed in production at Facebook for this purpose. Kome already owns the arithmetic it would need (the same `add256`/`sub256` used for RBSR prefix sums), which is consistent with why §3.1's deferred-digest verdict treats "incremental digest" as mechanically easy and correctly gates it on a real caller demonstrating need, not on feasibility.

**Blob layer.** Fixed-size chunking is field-normal as a *default* — IPFS defaults to 256 KiB fixed chunks; content-defined chunking (FastCDC, [Xia et al., USENIX ATC 2016](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)) is opt-in and pays off mainly for shifted-content dedup on large mutable files, not the "values usually small" personal-scale target Kome states. [iroh-blobs](https://github.com/n0-computer/iroh-blobs/blob/main/DESIGN.md) is the modern P2P reference (BLAKE3 verified streaming, 16 KiB chunk groups) and would mainly buy verified *partial* reads — marginal value here since each chunk is already a signed register. Kome's 32 KiB chunk size is rationally sized to its own transport/relay cap. Layering blobs as ordinary entities so RBSR, erasure, and GC apply uniformly mirrors how Willow attaches payloads to entries rather than running a second sync protocol.

**Cross-check of the Prolly/MST rejection.** The field agrees with `DECISIONS.md`. Dolt's prolly-tree documentation states its payoff is version-diffing across history at the cost of write amplification and chunk-size tuning ([Dolt storage engine docs](https://www.dolthub.com/docs/architecture/storage-engine/prolly-tree)); ATProto's MST exists to provide self-certifying, inclusion-provable repos with signed commits ([atproto repository spec](https://atproto.com/specs/repository)), a property Kome gets more directly from per-record EdDSA signatures. Merkle-CRDTs ([arXiv:2004.00107](https://arxiv.org/abs/2004.00107)) target a history-DAG transport Kome deliberately does not keep. Worth a periodic glance, not adoption: Automerge's [sedimentree](https://github.com/automerge/beelay/blob/main/docs/sedimentree.md) design, which is exploring storage/sync unification along similar lines to what §3.1's `content_gen`/`scope_gen` split and cached element hashes are edging toward, in a much smaller way.

## 5. Bottom line

Keep the nested `std::map` index, the Bitcask-style append-only log, and the flat sorted-vector-plus-prefix-sum RBSR snapshot. They are the structures the field converges on for this workload, and Kome's own measurements — sign/verify at 42–130 µs against container operations at nanoseconds to low microseconds — explain why no container swap can move a user-visible number. Make the five changes in §3.1: stream compaction, batch blob writes (with mandatory sub-frame flushing), cache the per-cell reconciliation-element hash, serve read-scoped snapshots as range views starting with time-bound-capability peers, and split the generation counter that gates snapshot rebuilds into a content half and a scope half. Benchmark, don't yet build, the four items in §3.2 — each has a real effect but a materially different size than first estimated, and two of them (encrypted-log verification skip, autocompaction knob) are posture or API-surface decisions that deserve a number in front of them before a maintainer commits to them. Treat §3.3 as settled: those eight structural alternatives were evaluated and each fails for a specific, checked reason, not a hand-wave — cite this document rather than re-running the analysis. The one genuinely open item this review surfaces but did not verdict-check is the recorded 64 KiB relay frame-size bug and its field-standard fix (a frame-size limit in the reconciliation layer); that is the natural subject of the next research pass.
