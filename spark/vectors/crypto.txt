# Kome.Crypto known-answer vectors. tests/test_crypto.adb reads them.
# Each line holds one vector. Single spaces separate the hex fields, and "-"
# is the empty byte string. A line that starts with "#" is a comment line.
#
# NORMATIVE (DESIGN.md §2 "strict"; AUDIT.md G16, H13, A25). Kome's
# Ed25519 verification predicate is: A (the public key) and R are canonical
# RFC 8032 §5.1.3 encodings; S < L; A is not one of the 8 canonical
# small-order encodings (the torsion subgroup, orders 1, 2, 4, 8); and the
# cofactored equation [8][S]B = [8]R + [8][k]A holds, with k = SHA-512 (R ‖
# A ‖ M) mod L. A small-order R is allowed. The wycheproof, ed25519_strict,
# ed25519_torsion and ed25519_small_order lines below are normative: every
# Kome verifier must give exactly these answers (the ed25519_torsion cases
# 3-5 separate the cofactored equation from the cofactorless one, and
# cases 0-1 and tcIds 152-159 separate "small-order A refused" from plain
# cofactored verification).
#
# Each value comes from a published test suite or from an implementation
# that is independent of monocypher:
#   blake2b256      Python hashlib.blake2b(digest_size=32) (RFC 7693 BLAKE2b).
#                   Lengths 127/128/129 and 255/256/257 cross the 128-byte
#                   block boundary.
#   blake2b256_keyed
#                   Python hashlib.blake2b(msg, key=key, digest_size=32)
#                   (RFC 7693 §2.10 keyed hashing, 32-byte key): the PRF
#                   f (key, msg) of DESIGN.md §6 (chain step, message
#                   "kome/prev") and §8 (bundle key, message "kome/bundle"
#                   ‖ ns); AUDIT.md G5. Lengths 127/128/129 cross the block
#                   boundary. The test main also requires that the keyed
#                   digest is not BLAKE2b-256 (key ‖ msg).
#   ed25519         RFC 8032 section 7.1 TEST 1, TEST 2 and TEST 3 verbatim
#                   (https://www.rfc-editor.org/rfc/rfc8032.txt, fetched
#                   2026-11-02, file SHA-256
#                   ed63657ff389301282b169b0abde9b5dd2c7e4d524fdfa5da6ff3094fc93c4c3):
#                   secret key (the 32-byte seed), public key, message,
#                   signature.
#                   Key_Pair, Derive_Public, Sign and Verify must reproduce
#                   them (DESIGN.md §1.2 D4: RFC 8032 Ed25519).
#   wycheproof      A subset of Wycheproof ed25519_test.json (C2SP/wycheproof,
#                   https://raw.githubusercontent.com/C2SP/wycheproof/main/
#                   testvectors_v1/ed25519_test.json, fetched 2026-11-02,
#                   file SHA-256 ea80ffebac085e21cb9d3e903e7fa2b448d96702da5b31f061d0b83b430b74b3,
#                   schema eddsa_verify_schema_v1.json, 210 tests, source of
#                   the groups google-wycheproof 0.9rc5). The fields are
#                   verbatim copies: tcId, result, the group's public key,
#                   msg, sig.
#                   Selected tcIds:
#                     valid: 1 2 3 7 80 81 82 84 86 114 119 181
#                     S >= L (s + L, 2L, 4L, 8L, 2^253, 2^254, 2^255, p;
#                       S just above L): 63-70, 85
#                     non-canonical R (y = 1 with the sign bit set): 151;
#                       R sign flipped, R = 0, invalid R: 59 60 61
#                     truncated or wrong length: 30 (empty), 31 (s missing),
#                       32 (62 bytes), 33 (66 bytes), 38 (63 bytes)
#                     mixed-order public key regression: 210
#                     small-order public keys (flag SmallOrderPublicKey,
#                       result "acceptable" in Wycheproof; Kome refuses
#                       them, H13, so the lines here say "invalid"):
#                       152-159. Their public keys are the 8 encodings of
#                       the ed25519_small_order lines.
#                   The test main requires Verify = (result = valid) for each
#                   64-byte signature. For the other signatures, it requires
#                   that the bytes cannot become a Sig (a length check).
#                   All 210 tests also ran through the same strict check in
#                   C (a scratch harness, not committed): the check accepted
#                   each "valid" test and rejected each "invalid" test.
#                   Plain crypto_ed25519_check accepts tcId 151 (see
#                   kome-crypto.ads, STRICT VERIFICATION).
#   ed25519_torsion The 12 cases of ed25519-speccheck ("Taming the many
#                   EdDSAs", Chalkias, Garillot, Nikolaenko, SSR 2020;
#                   https://raw.githubusercontent.com/novifinancial/
#                   ed25519-speccheck/master/cases.json, fetched 2026-11-04,
#                   file SHA-256
#                   08e47a36d9aead288664930505584f353fff113ab854f2800db1e4f5b3540450),
#                   verbatim: case number, Kome's expected answer, pub_key,
#                   message, signature. The expected answers follow from
#                   the normative predicate above and were computed with
#                   it in plain Python integers (RFC 8032 §5.1 arithmetic,
#                   no library): cases 0 and 1 have a small-order A
#                   (refused); 2 has a small-order R under a good A
#                   (accepted); 3, 4 and 5 pass the cofactored equation
#                   only (accepted: they would fail under a cofactorless
#                   verifier); 6 and 7 have S >= L; 8 and 9 a non-canonical
#                   R; 10 and 11 a non-canonical A (all refused).
#   ed25519_small_order
#                   The 8 canonical encodings of the small-order points
#                   (order, encoding). Derived in plain Python integers: the
#                   points with y in {1, p - 1, 0} and the two roots of
#                   d y^4 + 2 y^2 - 1 = 0 (the order-8 points, x^2 = -y^2),
#                   each with both signs of x where x /= 0, kept when the
#                   decoded point re-encodes to the same bytes; the order of
#                   each was checked by point multiplication. They are the
#                   public keys of Wycheproof tcIds 152-159 and libsodium's
#                   ge25519_has_small_order list (without its non-canonical
#                   entries). The test main requires Is_Small_Order_Point
#                   and Is_Canonical_Point, and that Verify refuses the
#                   signature (R = identity, S = 0), which satisfies the
#                   cofactored equation for every such key (universal
#                   forgery without the check).
#   ed25519_strict  Non-canonical encodings that plain crypto_ed25519_check
#                   accepts and Verify must reject. Each is paired with its
#                   canonical control. Generated with Python (hashlib.sha512
#                   and integers) for the RFC 8032 TEST 1 key and the
#                   message "kome strict". R is a small-order point, so with
#                   S = SHA-512(R ‖ A ‖ M) * a mod L, the cofactored equation
#                   [8][S]B = [8]R + [8][k]A holds. The controls verify under
#                   both the plain and the strict check. The non-canonical
#                   lines verify under the plain check only (checked with the
#                   same C harness). The last two lines are a non-canonical
#                   public key (the identity as y = p + 1, and as y = 1 with
#                   the sign bit set), with the signature R = identity,
#                   S = 0.
#   x25519          RFC 7748 section 5.2 (cross-checked with pyca/cryptography).
#   x25519dh        RFC 7748 section 6.1 Alice/Bob exchange.
#   x25519_low      Low-order u-coordinates: 0, 1, the order-8 points
#                   e0eb7a7c... and 5f9c95bc... (libsodium's low-order
#                   blocklist; RFC 7748 §6.1 says to check for all zeros),
#                   p - 1, and the non-canonical encodings p and p + 1. Each
#                   scalar gives an all-zero shared secret (pyca/cryptography
#                   refuses each one with "Error computing shared key").
#                   X25519 must report Contributory = False.
#   dh_key          Known answers for Is_Reduced_U and Is_Low_Order_U (and
#                   thus for Is_Good_DH_Key = reduced and not low order), by
#                   definition (DESIGN.md §2 rule 3, E5). The five reduced
#                   low-order encodings are reduced and low order. p, p + 1,
#                   2^255 - 1 and all values with bit 255 set are not
#                   reduced. The RFC 7748 §6.1 public keys and the base
#                   point u = 9 are good keys.
#   aead            XChaCha20-Poly1305, IETF construction (monocypher 4
#                   crypto_aead_lock). The first line is
#                   draft-irtf-cfrg-xchacha-03 appendix A.3.1. The other
#                   lines are computed with HChaCha20 (checked against 2.2.1
#                   of the draft) plus pyca/cryptography ChaCha20Poly1305.
#
